# Tuoshi LT22M / ML352 — local integration, not yet an upstream release

This local worktree is based on upstream/main 07b82d795314bde3769328e51acc472b9855fc5c
(2026-11-17), including the upstream `cell_lock.uc` dialect table. The old
`wwand-review` prototype is NOT installed or upstream. Matching board files
live in `lt22m-local-feed/collections/lt22m-wwand/`; local LuCI additions
remain in `firmware-research/wwand-luci-app-review/`.
The first local fullflash test image was installed on 2026-11-16; the revised
image (SHA256 bcebc6f064b28e0d65156c238781eb3fd8a40d2828184c588f2430d3f0fa267d)
was installed on the LT22M at 192.168.5.1 with configuration preservation
on 2026-11-17 after `sysupgrade -T` passed. The sysupgrade ubus handoff
reported a lost connection, but the device rebooted into the new image;
post-boot installation, protected MTD hashes and LTE traffic were checked.
The ML352 changes are carried in a local fork branch; no ddimension upstream
PR, merge or wwand release is claimed.

## Device measurements (ML352_AFL-V1, LT22M, 2026-11-16)

- Before migration the RNDIS data link was `eth1`, ARP enabled
  (`flags=0x1003`). wwand now renames that same USB netdev to `wwand0`
  (observed `NOARP` after boot); the DHCP child on `wwand0` still gets the
  correct address 10.199.103.90/8 and gateway 10.199.103.165 and bound LTE
  pings succeed. `AT+CGCONTRDP=1` exposes the PDP address and two DNS servers,
  but its gateway and subnet fields are empty. A temporary gateway-free /32
  host route on wwand's `NOARP` link passed three bound pings; the native wwand
  /32 + device-default path obtained the address and route but **not DNS**
  because our ML352 adapter previously read only `AT+CGPADDR`. The local
  adapter now merges `AT+CGCONTRDP` DNS only for the same assigned PDP address.
  The revised image now uses this native route: post-boot parent `lte` holds
  one IPv4 address, two carrier DNS servers and a gateway-free default device
  route on NOARP `wwand0`; bound traffic and a controlled ifdown/ifup passed.
- Serial AT control `/dev/ttyUSB1`. Only one manager may own it; migrating an
  existing device first retires/disables `ml352d`. A read-only EEM sample can
  be taken without interrupting data (observed 0/3 lost pings), but the mode
  must be restored even when the EEM query times out.
- Serving cell in the measured sample: LTE B7, EARFCN 3050, PCI 312.
  `+EEMLTEINTER` reports measured neighbours as PCI, EARFCN and raw RSRP/RSRQ
  indices. It does NOT report their PLMN or globally unique ECI. A neighbour
  being visible does not prove the SIM may register on it, and it is not a CA
  carrier. Do not interpret anomalous `+EEMLTESVC` field 1 (`610`) as a PLMN.
- `AT*CELL?` returns `+CME ERROR: operation not supported`; no lock readback
  or previous-state snapshot exists. `AT*CELL=2,3,7,3050,312` and clear
  `AT*CELL=0` caused `NO CARRIER`, modem re-registration and a stale DHCP
  lease. A previous manual recovery required PDP deactivation/activation,
  `AT*NETACT=1,1,1` and a netifd DHCP restart. The fresh wwand dial now
  runs `AT+CGACT=1,<cid>` **before** `AT*NETACT=1,<cid>,1`; initial wwand
  connectivity works, but the forced-failure recovery sequence has NOT yet
  been verified live.

## Build/image ownership

- The two board IDs, `tuoshi,lt22m` and `tuoshi,lt22m-fullflash`, install
  separate JSON board profiles using wwand's modular `tech` LEDs and `sweep`
  (blue:mobile-2/3/4). GPIO1 is a USB-enable hog, GPIO38 a user button;
  neither is a proven independent modem reset GPIO. They remain absent from
  the profiles: GPIO1 is kernel-claimed as a boot-critical USB-enable hog;
  GPIO38 is the reset-button input/IRQ. wwand needs an exposed sysfs line and
  cannot actuate either hogged line. Live recovery is armed at zero attempts:
  default rungs 8 (CFUN 0/1), 16 (CFUN=1,1), 24 (ineffective board repower
  without hardware). `failreboot=0` preserves management instead of rebooting;
  zero-RX defaults to six hours, TX-stall to 120 seconds and sampling is every
  15 seconds. No physical reset or forced-recovery test has run. Modern tech
  LEDs indicate RAT registration, NOT the old daemon's stricter PDP+IP-ready
  state; the sweep period is 300 ms.
- The installed revised image uses `wwand_modem ml352` (NCM, `eth1`,
  `/dev/ttyUSB1`) and `interface lte proto wwand`, `pdp_type ipv4`, without the
  local `ipv4_dhcp` extension. On the known previous migration, the board-gated
  default removed the obsolete flag at first boot: the dynamic `lte_4` DHCP
  child is absent; native `lte` owns the IPv4 address, gateway-free device
  route and two matching modem-supplied DNS servers on `wwand0`. Custom LTE
  profiles remain untouched by that cleanup.
- Stock and fullflash profiles deselect `ml352d`, `luci-app-ml352` and the
  previous modem UI package. The old stock-only source tree has no
  `lt22m-bootloader` helper; its **local** wwand image cannot perform a
  stock→fullflash loader migration. The fullflash build includes that helper.
  Release image verification still requires it and has no exception unless
  explicitly invoking the local-only stock verifier override. The release
  workflow deliberately fails closed:
  feed recipe SHA and wwand source pin/hash must be updated only AFTER this
  source and LuCI are tested and committed at the operator's request. For
  local tests, stage **copies** of uncommitted source and run a package-local
  `make -C package/feeds/ddimension/wwand TOPDIR="$PWD"
  USE_SOURCE_DIR=<absolute-staged-source> compile`: a top-level `make
  package/wwand/compile USE_SOURCE_DIR=...` propagates the override to every
  dependency and can wrongly symlink a kernel package to the wwand tree.

## Environment and unsupported ML352 cell lock

EEM telemetry records serving and intra-/inter-frequency neighbours in the
standard **read-only** `modem_cells` shape. RSRP/RSRQ values remain raw indices
(`rsrp_index`, `rsrq_index`, `metric_encoding: raw_eem_index`), NOT dBm/dB
without an independently verified encoding. Serving operator comes from the
regular registration/COPS source; neighbour operator remains unknown.

wwand's existing network selection chooses a PLMN (`AT+COPS` on NCM), not a
specific EARFCN:PCI. Upstream 07b82d7 moved `lock_4g` to `cell_lock.uc`:
Quectel QNWLOCK and QMI NAS dialects require a successful read before any
write. ML352's `AT*CELL?` is unsupported, so it has **no dialect entry**;
configured lock options produce an unapplied warning, never an ML352 or
Quectel lock write. The LuCI editor hides persistent locking on ML352. The previous flashed
test image included an experimental ML352 90-second selection API; it was
never run and had no crash-safe rollback. The installed revision removes
that API and its LuCI controls. **ML352 neighbour-cell selection is not
available**; read-only serving and neighbour rows still work.

## Validation: offline and on-device

1. Against upstream 07b82d7 on the target's ucode, `test_cell_lock` passed
   71 checks (including an ML352 unsupported-read/no-write regression),
   `test_atcmd` 331, `test_config` 500, `test_ml352_ip` 11, `test_board` 263,
   `test_modem_common` 403 and `test_ubus` 15. The isolated ML352 scenario of
   `test_ncm` passed 195 checks. The **complete** NCM suite still aborts in
   `context_ncm.uc:877` on the test runtime's null-function callback; the same
   class of failure occurred on unchanged earlier upstream. The host lacks
   `ucode`, so its full `run_tests.sh` cannot run there. This is not a green
   complete test suite.
2. **Offline completed:** the revised fullflash image was built from staged
   local wwand/LuCI source on upstream 07b82d7 rather than the still-pinned
   older feed source. The first build exposed a missing `cell_lock.uc` package
   install entry; after fixing the feed Makefile and rebuilding, extracted
   SquashFS contains both its compiled dialect and ML352 recipe. The image
   verifier checked kernel magic/CRC, size, board metadata and manifests.
   SHA256 is `bcebc6f064b28e0d65156c238781eb3fd8a40d2828184c588f2430d3f0fa267d`;
   the router checked the matching staged hash and passed `sysupgrade -T`.
   Exact build source and preflash MTD/config backups are stored privately
   off-device; release source pins/hashes are deliberately not published.
3. **Live installation completed on fullflash LT22M:** the ordinary
   configuration-preserving fullflash sysupgrade rebooted into the revised
   image, despite reporting a dropped ubus connection at handoff. The modem's
   NCM context is CONNECTED; parent `lte` owns one IPv4 address, two carrier
   DNS servers and a gateway-free default route on NOARP `wwand0`. `lte_4` and
   the old `ipv4_dhcp` flag are absent; the APN remains configured, and bound
   LTE IP and hostname pings pass. After a controlled `ifdown lte; ifup lte`,
   context, parent IPv4/DNS and bound LTE traffic recovered. The LuCI asset
   returned HTTP 200; read-only `modem_cells` exposed the serving B3 EARFCN
   1300 PCI 47 and a neighbour. Pre- and post-flash SHA256 hashes of mtd0
   bootloader, mtd1 environment and mtd2 Factory are identical; mtd3 firmware
   alone was upgraded. A workstation reboot after installation did not disturb
   the router: 23 minutes uptime, CONNECTED and bound traffic passed again.
4. A second fullflash LT22M (2026-11-22) retained its 192.168.190.1 LAN and
   distinct protected MTD hashes across the upgrade. A preserved legacy
   `eth1` name no longer resolved after RNDIS became `wwand0`; setting the
   stable USB path `1-1` restored discovery. This ML352 firmware refused a
   repeated `CGACT=1,1` with CME while `CGACT?` reported CID 1 active. The
   tested adapter now reads state first and skips the redundant command.
   Following a corrected image upgrade, an unset APN yielded a PDP address,
   native LTE IPv4, two DNS servers, bound IP/hostname traffic and a successful
   `ifdown lte; ifup lte` reconnect. The site's supplied SIM PIN was saved
   only in the router's UCI; no SIM lock was enabled here.
5. Still outstanding for an upstream PR: resolve the full NCM suite's
   unrelated test-runtime failures and test forced modem failure/recovery.
   Firmware package source pins/hashes belong to the LT22M release workflow,
   not an upstream wwand-release claim.

### Remaining hardware limits

Do not configure `reset_gpio` until the independent ML352 reset net, polarity
and exported sysfs line are proven: GPIO1 is a USB-enable hog and GPIO38 is
the operator's reset button. An `ifdown`/`ifup` confirms ordinary interface
reconnect, not the forced-failure recovery ladder or a hardware reset. Since
`AT*CELL?` is unsupported, no ML352 dialect can meet upstream's read-before-
write lock contract; the older experimental cell trial is not in this image.
